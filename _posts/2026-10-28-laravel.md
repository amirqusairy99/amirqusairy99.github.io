Modern web application development often requires stitching together multiple cloud services to create a scalable, secure, and feature-rich platform. For my project, `letsbelajar.tech`, I designed an architecture that leverages PHP/Laravel for business logic, Heroku for deployment simplicity, Firebase for scalable infrastructure, and Cloudflare for network security and DNS.

In this post, I will break down the system architecture diagram I created to visualize how these components interact.

## The Architectural Blueprint

Before diving into code or server configuration, I created this high-level diagram to map out data flow and service responsibilities.

![Detailed System Architecture Diagram for letsbelajar.tech]({{ page.image | relative_url }})
*Figure 1: High-Level System Architecture Diagram*

Let's dissect each section of this stack, starting from the end-user and moving deeper into the backend infrastructure.

---

## 1. The Entry Point: Users, DNS, and Subdomains

The flow begins at the bottom of the diagram with **End Users** making requests.

### Domain Strategy and Subdomains

The application manages multiple lifecycle stages using subdomains.

*   `letsbelajar.tech`: The primary root domain.
*   `app.letsbelajar.tech`: The main production application interface.
*   `demo.letsbelajar.tech`: A public-facing showcase environment.
*   `staging.letsbelajar.tech`: A private pre-production environment for testing.

### The Role of Cloudflare DNS

To route traffic securely and efficiently, I utilize **Cloudflare DNS**. In this diagram, you can see traffic flow from the main `DNS` node (the internet) through the specific `Cloudflare DNS` component. This provides crucial benefits:

*   **Fast DNS Resolution**: Cloudflare provides one of the fastest DNS services globally.
*   **Edge Security**: While not explicitly labeled for WAF (Web Application Firewall) or DDoS protection in this diagram, incorporating Cloudflare DNS allows me to easily enable these proxy services to protect my Heroku origin server.
*   **Flexible Routing**: DNS records (CNAMEs) point `letsbelajar.tech` and its subdomains directly to the application running on Heroku.

---

## 2. The Core Application: Heroku and Laravel

Once DNS resolves the request, traffic is routed to the central component of the stack: the **Heroku Server**.

### The Heroku Platform-as-a-Service (PaaS)

I chose Heroku for this deployment due to its simplicity and streamlined developer experience (Git-based deployment).

*   **Web Server / API**: This component represents the running web application dynos. These dynos handle the HTTP requests for both the main application (`app`) and the API that powers the interfaces.
*   **PHP / Laravel**: Under the hood, this is a standard PHP application built on the **Laravel** framework, which manages all business logic, routing, and controller functions.

### The Relational Database: Heroku Postgres

Every robust web application needs a structured way to store data. The diagram shows the `Heroku Server` connecting directly to a **Heroku Postgres Database**.

This managed relational database stores primary application data, such as:

*   User account details (non-sensitive fields).
*   Application-specific content (lessons, comments, status).
*   Activity logs.

Storing the database within the Heroku ecosystem minimizes latency and simplifies backups.

---

## 3. Extending Functionality: Firebase Integrations

The true power of this modern stack comes from offloading complex, specialized tasks to Google’s Firebase platform. This allows me to scale these specific services independently of my core web server.

### A. Firebase Authentication: A Unified Identity Service

The first connection from the Heroku Server points to **Firebase Authentication**.

Authentication can be complex to manage securely. I use Firebase as a **Unified Authentication Service**, which solves two major problems:

*   **External Provider OAuth (Google, etc.)**: Firebase Auth handles the intricate handshake required for "Sign in with Google," "Sign in with GitHub," or other social logins.
*   **Native Laravel Auth Integration**: By integrating Firebase Auth with Laravel's built-in authentication system, I can use Laravel's familiar middleware and guards (`Auth::check()`, `Auth::user()`) while offloading the password hashing and session management to Firebase.

This architecture ensures high security for user credentials and provides a seamless login experience.

### B. Firebase Storage: Scalable Asset Hosting

The second connection from the Heroku Server points to **Firebase Storage**.

I use the Firebase Storage **(free tier)** to host application assets. Offloading file storage from the Heroku dynos is a critical best practice.

Heroku dynos use an ephemeral file system (files uploaded to the disk disappear when the dyno restarts). By using Firebase Storage (which is built on Google Cloud Storage), I get:

*   **Persistent Storage**: Files are saved permanently.
*   **High Availability**: Assets are served reliably globally.
*   **Scalability**: The free tier covers initial development, and scaling requires zero code changes.

The application uses this to store user uploads, avatars, static documents, and lesson images.

---

## Conclusion

This diagram represents a robust and scalable architecture for a modern web project. By utilizing Cloudflare for DNS security, Heroku for simple deployment, and Firebase for specialized authentication and storage services, I can focus on building the core application logic in Laravel without worrying about infrastructure management or security fundamentals from scratch.

While the current setup utilizes the Firebase free tier effectively, this architecture is designed for growth and can easily be scaled or optimized as `letsbelajar.tech` evolves.
