Deploying your first full-stack application to the cloud can be daunting. You have a frontend, a Node.js/Express backend, and a MySQL database, but how do they all fit together in a production environment? 

In this post, we'll break down a classic 3-Tier Architecture on AWS, discuss the recent changes to the AWS Free Tier, and make some critical architectural decisions before we start spinning up servers.

## 1. The Conceptual 3-Tier Architecture

A 3-tier architecture physically and logically separates your application into three distinct layers:

1. **Presentation Tier (Frontend):** Static HTML/CSS/JS files that run in the user's browser.
2. **Application Tier (Backend):** Our Node.js / Express.js REST API, which handles business logic and background schedulers.
3. **Data Tier (Database/Storage):** Our relational database (MySQL) and persistent file storage.

Here is a high-level look at how we will map this to AWS:

```text
                  [ Clients / Web Browsers ]
                              │
                              ▼ 
                 [ AWS EC2 (t2/t3.micro) ]
                 ├── Nginx Reverse Proxy (Port 80/443)
                 │     ├── Serves Static Assets (Frontend)
                 │     └── Proxies /api to Node.js
                 └── Node.js / Express API (Port 3000)
                              │
           ┌──────────────────┴──────────────────┐
           ▼                                     ▼
[ Amazon RDS for MySQL ]               [ Amazon S3 (Uploads) ]
- Single-AZ Deployment                 - Persistent storage for
- Stores application data                user-uploaded files
```

## 2. The New AWS "Free Tier" Reality (Important Update)

If you are reading older AWS tutorials, you might see references to the "12-Month Free Tier" (e.g., 750 free hours of EC2). **Be warned: AWS changed this model for new accounts.**

New AWS accounts now operate on a credit-based system. You receive an initial credit grant (usually around $100) that expires after 6 months. Your S3, EC2, and RDS usage will immediately bill against this credit pool. 

**Crucial Note:** AWS now charges for public IPv4 addresses (~$3.60/month per IP). Your EC2 instance will need one to communicate with the internet, so keep an eye on your billing dashboard and set up an AWS Budget alert immediately!

## 3. Key Architectural Decisions

Before touching the AWS console, we had to make two major decisions regarding our deployment strategy. 

### Decision 1: Frontend Hosting — EC2/Nginx over S3/CloudFront
* **The Choice:** We are hosting both the static frontend and the Node.js backend on a single EC2 instance, using Nginx as a reverse proxy. 
* **The Why:** While hosting a frontend on S3 distributed by CloudFront is a best practice for massive scale, it introduces complex networking and CORS (Cross-Origin Resource Sharing) headaches. By keeping everything on one EC2 instance behind Nginx, we simplify the deployment, consolidate resources to save our AWS credits, and make configuring SSL (HTTPS) much easier.

### Decision 2: File Uploads — S3 over Local EC2 Disk
* **The Choice:** We will configure our Node.js app (using `multer-s3`) to send user uploads directly to an Amazon S3 bucket.
* **The Why:** It's tempting to just save files to the `/uploads` folder on the EC2 server. However, EC2 local storage is *ephemeral*. If our server crashes, gets terminated, or needs to be replaced, all user files would be permanently lost. Routing uploads to S3 guarantees our data is safe and teaches us a fundamental cloud-native pattern.

## 4. High-Level Implementation Roadmap

With our architecture decided, our deployment will follow these four phases:

1. **Phase 1: AWS VPC & Networking Setup**
   * Configure Security Groups to allow public web traffic (Ports 80/443) to our EC2 server, but restrict database access so only our EC2 server can talk to our RDS instance.
2. **Phase 2: Database Provisioning**
   * Launch the RDS MySQL instance and run our database seeding scripts to set up our tables.
3. **Phase 3: Application Server Setup**
   * Launch our EC2 instance, install Node.js, PM2 (to keep the app running 24/7), and clone our code.
4. **Phase 4: Web Server & Domain/SSL**
   * Install Nginx to serve our frontend files and route API traffic to our Node app. Finally, secure it with a free SSL certificate from Let's Encrypt.
